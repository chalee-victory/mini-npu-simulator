# Mini NPU Simulator

AI가 계산하는 방식(MAC 연산)을 흉내 내는 작은 Python 콘솔 계산기입니다.
숫자 배열로 된 입력 패턴을 십자가(Cross) 필터와 X 필터에 각각 곱하고 더해(MAC) 점수를 구하고,
점수를 비교해 패턴이 어느 모양에 더 가까운지 판정합니다.

## 실행 환경

- Python 3.8 이상
- 외부 라이브러리 없이 표준 라이브러리(`json`, `os`, `time`)만 사용

## 실행 방법

```bash
python main.py
```

실행 후 모드를 선택합니다. 1, 2, 3이 아닌 값을 입력하면 다시 선택하라는 안내가 나옵니다.

1. **사용자 입력 (3×3)**: 필터 A, B와 패턴을 콘솔에 직접 입력 (필터는 `y`를 입력하면 십자가/X로 자동 생성)
2. **data.json 분석**: `data.json`의 필터와 패턴을 읽어 일괄 판정
3. **보너스**: 패턴 생성기로 N×N 십자가/X 패턴을 만들고, 2차원/1차원 MAC 성능 비교

`data.json`은 `main.py`와 같은 폴더에 두어야 합니다. 프로그램은 `main.py` 위치를 기준으로 파일을 찾으므로, 다른 폴더에서 실행해도 동작합니다.

### 모드 1 입력 예시

필터 입력 전에 자동 생성 여부를 묻습니다. 엔터를 누르면 직접 입력, `y`를 입력하면 필터 A(십자가), B(X)가 자동으로 만들어집니다.
직접 입력할 때는 각 줄에 숫자 3개를 공백으로 구분해 입력합니다.

```
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0
```

### 의도적 오류 데이터로 실행

`bad_data.json`에는 크기 불일치, 라벨 오류, 키 형식 오류 등을 일부러 넣어 두었습니다. 아래 명령으로 메뉴 없이 모드 2 분석만 실행할 수 있습니다.

```bash
python -c "import main; main.run_mode2('bad_data.json')"
```

## 구현 요약

### 필터와 패턴

- **필터**: 판정의 기준이 되는 배열입니다. Cross 모양 기준, X 모양 기준처럼 미리 정해 둡니다.
- **패턴**: 판정받을 입력 배열입니다.
- 패턴 하나를 필터 두 개에 각각 MAC 연산해 점수를 구하고, 점수가 더 높은 필터의 이름으로 판정합니다.

### MAC 연산: `mac(pattern, flt)`

- 입력 패턴과 필터를 같은 위치(`i`행 `j`열)끼리 곱한 뒤 모두 더해 점수를 반환합니다.
- NumPy 같은 외부 라이브러리 없이 이중 `for` 반복문으로 직접 구현했습니다.
- `len(pattern)`으로 크기 N을 구하므로 3×3부터 25×25까지 크기와 상관없이 동작합니다.
- N×N 배열이면 곱셈과 덧셈을 각각 N²번 수행합니다.

### 라벨 정규화: `normalize_label(label)`

데이터에 섞여 있는 여러 표기를 프로그램 내부의 표준 라벨 두 가지(`Cross`, `X`)로 통일합니다.

| 입력 표기 | 표준 라벨 |
|---|---|
| `+`, `cross` (대소문자, 앞뒤 공백 무관) | `Cross` |
| `x` (대소문자, 앞뒤 공백 무관) | `X` |
| 그 밖의 값 | `None` (호출한 쪽에서 라벨 오류로 처리) |

- 먼저 `strip()`으로 앞뒤 공백을 지우고 `lower()`로 소문자로 바꾼 뒤, 대응표(`LABEL_MAP`)에서 찾습니다.
- 대응표에서 `get()`으로 찾기 때문에, 알 수 없는 라벨이 들어와도 오류로 멈추지 않고 `None`을 반환합니다.
- 모드 2에서는 필터 키(`cross`, `x`)와 expected 값(`+`, `x`) 모두 이 함수를 거친 뒤 비교합니다. 정규화하지 않으면 `"x" == "X"`가 거짓이 되어 올바른 판정도 FAIL이 됩니다.

### 판정과 동점 처리: `judge(score_a, score_b, label_a, label_b)`

- 컴퓨터는 소수를 2진수로 정확히 저장하지 못해 `0.9`와 `0.8999999999999999`처럼 사실상 같은 값에 미세한 차이가 생깁니다.
- 그래서 `abs(score_a - score_b) < 1e-9`이면 동점(`UNDECIDED`)으로 판정하는 허용오차(epsilon) 정책을 적용했습니다.
- 동점 검사를 가장 먼저 수행합니다. 크기 비교(`>`)를 먼저 하면 미세한 차이만으로 한쪽이 이긴 것으로 판정되기 때문입니다.
- 이긴 쪽 이름을 매개변수(`label_a`, `label_b`)로 받아, 모드 1(`A`/`B`)과 모드 2(`Cross`/`X`)에서 같은 함수를 사용합니다.

### 모드 1 입력과 검증: `read_matrix(name, n=3)`

n줄을 한 줄씩 입력받아 n×n 실수(float) 배열로 반환합니다. 필터 A, 필터 B, 패턴 입력에 같은 함수를 사용합니다.

- 한 줄을 입력받을 때마다 두 가지를 순서대로 검사합니다.
  1. **열 개수**: `split()`으로 나눈 조각이 n개가 아니면 오류
  2. **숫자 형식**: 각 조각을 `float()`로 바꾸다 `ValueError`가 나면 오류 (`try / except`로 처리해 프로그램이 멈추지 않음)
- 오류가 나면 원인(입력된 개수 또는 입력값)과 몇 번째 줄인지를 안내하고, `continue`로 **그 줄만** 다시 입력받습니다.
- 검사를 통과한 줄만 저장하고, 정상 줄이 n개 모일 때까지 반복하므로 **행 개수는 항상 n**이 됩니다.
- `split()`을 구분자 없이 사용해 공백이 여러 개이거나 앞뒤에 공백이 있어도 정상 처리합니다.

### 모드 2 data.json 분석: `run_mode2(path=DATA_FILE)`

```
data.json 읽기 → [1] 필터 로드(라벨 정규화) → [2] 패턴마다: 키에서 N 추출 → 필터 선택 → 검증 → MAC → 판정 → PASS/FAIL
              → [3] 성능 분석 → [4] 결과 요약
```

| 함수 | 역할 |
|---|---|
| `load_json(path)` | 파일을 읽어 딕셔너리로 변환. 파일이 없거나(`FileNotFoundError`) JSON 형식이 깨져도(`JSONDecodeError`) 멈추지 않고 안내 |
| `get_size(key)` | `size_13`, `size_13_2` 같은 키를 `_`로 나눠 두 번째 조각을 숫자로 바꿔 크기 13을 추출. 형식이 틀리면 `None` |
| `load_filters(data)` | 필터 키 `cross`/`x`를 `Cross`/`X`로 정규화하고, Cross와 X가 모두 정상인 크기만 `{N: {"Cross": 배열, "X": 배열}}` 형태로 정리 |
| `check_matrix(matrix, n)` | n×n 숫자 배열인지 검사. 정상이면 빈 문자열, 문제가 있으면 사유(행 개수, 열 개수, 숫자 아님)를 반환 |
| `analyze_pattern(key, item, filters)` | 패턴 하나를 검증하고 판정한 결과를 딕셔너리(점수, 판정, expected, PASS 여부, 실패 사유)로 반환 |
| `print_pattern_result(r)` | 결과 딕셔너리를 화면에 출력 |

- `run_mode2()`의 매개변수 `path`는 기본값이 `DATA_FILE`(main.py와 같은 폴더의 data.json)입니다. 메뉴에서는 기본값을 쓰고, 테스트할 때는 `run_mode2('bad_data.json')`처럼 다른 파일을 넣을 수 있습니다.

**케이스 단위 FAIL 처리**: `analyze_pattern()`은 아래 순서로 검사하고, 하나라도 걸리면 사유를 남기고 즉시 반환합니다. MAC 연산은 모든 검사를 통과한 경우에만 수행하므로, 크기가 다른 배열 때문에 `IndexError`로 프로그램이 멈추는 일이 없습니다.

1. 패턴 키 형식 (`size_N_idx`)
2. 해당 크기의 필터 존재 여부
3. expected 라벨이 표준 라벨로 정규화되는지
4. 패턴이 필터와 같은 n×n 숫자 배열인지
5. MAC 연산 → 판정 → expected와 비교 (동점이면 UNDECIDED로 FAIL)

계산(`analyze_pattern`)과 출력(`print_pattern_result`)을 나누고 결과를 목록으로 반환하도록 해, 결과 요약에서 같은 데이터를 다시 사용합니다.

### 성능 측정: `measure_mac(pattern, flt, repeat=10, func=mac)`

- 워밍업으로 `mac()`을 1회 먼저 실행한 뒤, 10회 반복 실행한 전체 시간을 `time.perf_counter()`로 잽니다. 10으로 나누고 ms 단위로 바꿔 1회 평균 시간을 반환합니다.
- 측정 구간에는 `mac()` 호출만 포함하고, 입력(`input`), 출력(`print`), 파일 읽기 시간은 제외했습니다.
- 워밍업은 첫 호출에만 생기는 준비 비용이 측정값에 섞이지 않게 하기 위한 것입니다.
- 측정할 함수를 매개변수 `func`(기본값 `mac`)로 받아, 보너스의 1차원 MAC(`mac_flat`)도 같은 방식으로 측정합니다.

### 성능 분석과 결과 요약

| 함수 | 역할 |
|---|---|
| `run_performance(filters)` | 3×3(패턴 생성기 `make_cross(3)`, `make_x(3)`)과 data.json의 각 크기 필터로 `measure_mac()`을 실행해 `[(N, ms), ...]` 반환. data.json에는 3×3 필터가 없어 생성기로 만듦 |
| `print_performance_table(rows)` | 크기(N×N) / 평균 시간(ms) / 연산 횟수(N²) 표 출력 |
| `print_summary(results)` | 모드 2 결과 목록에서 통과하지 못한 항목을 골라 전체/통과/실패 수와 실패 케이스, 사유 출력 |

- 모드 1은 마지막에 3×3 한 줄짜리 성능 표를, 모드 2는 3×3, 5×5, 13×13, 25×25 네 줄짜리 표를 출력합니다.
- 표 제목에는 한글이 있어 화면에서 2칸을 차지하므로, f-string 칸 맞춤 대신 공백을 직접 넣어 숫자 줄과 맞췄습니다.

### 보너스 1: 패턴 생성기

| 함수 | 역할 |
|---|---|
| `make_cross(n)` | 가운데 행(`i == n // 2`)과 가운데 열(`j == n // 2`)이 1.0인 n×n 십자가 패턴 생성 |
| `make_x(n)` | 두 대각선(`i == j`, `i + j == n - 1`)이 1.0인 n×n X 패턴 생성 |
| `print_matrix(matrix)` | 패턴을 ■(0이 아닌 값)와 □(0)로 화면에 그림 |
| `read_size()` | 크기 N 입력 (3~51, 엔터 = 5). 정수가 아니거나 범위 밖이면 다시 입력 |

**재활용한 곳**
- 모드 1: 필터 입력 단계에서 `y`를 입력하면 필터 A, B를 생성기로 만듭니다.
- 성능 분석: 3×3 측정에 쓰던 고정 배열을 `make_cross(3)`, `make_x(3)`으로 바꿨습니다.
- 모드 3: 입력한 N으로 패턴을 만들어 그리고, 생성한 패턴이 각각 Cross와 X로 올바르게 판정되는지 확인합니다. 예를 들어 7×7이면 십자가 패턴은 Cross 13.0 / X 1.0, X 패턴은 Cross 1.0 / X 13.0으로 판정됩니다.
- N의 최솟값을 3으로 둔 이유: 2×2에서는 십자가와 X가 거의 같은 모양이 되어 판정이 의미가 없기 때문입니다.

### 보너스 2: 1차원 배열 최적화

| 함수 | 역할 |
|---|---|
| `flatten(matrix)` | n×n 2차원 배열을 행 순서대로 이어 붙여 길이 n²의 1차원 리스트로 변환 |
| `mac_flat(a, b)` | 1차원 리스트를 반복문 1개, 인덱스 1개(`a[k] * b[k]`)로 MAC 연산 |

- 2차원 `mac()`은 `pattern[i][j]`처럼 행을 찾고 다시 열을 찾는 두 단계 접근과 이중 반복문을 씁니다. 1차원 `mac_flat()`은 `a[k]` 한 단계 접근과 반복문 하나로 같은 계산을 합니다.
- 같은 행 순서로 더하므로 두 방식의 점수는 소수점 끝자리까지 완전히 같습니다(비교표의 "점수 일치" ✓).
- 공정한 비교를 위해 **같은 입력**(생성기로 만든 십자가와 X)과 **같은 반복 횟수**(각 1000회, 워밍업 1회)로 측정했습니다. 1차원 변환(`flatten`)은 측정 전에 한 번만 하므로 측정 시간에서 제외했습니다. 비교에서 반복을 1000회로 늘린 이유는, 두 방식의 차이가 매우 작아 10회 측정으로는 오차가 차이보다 커지기 때문입니다.

### 모드 2 (bad_data.json, 의도적 오류)

프로그램이 멈추지 않고 케이스 단위로 처리되며, 결과 요약은 총 7 / 통과 1 / 실패 6입니다.

| 항목 | 넣어 둔 오류 | 출력 |

## 결과 리포트

### 1. 실패 원인 분석

data.json 분석 결과 6개 중 3개(size_5_1, size_13_2, size_25_1)가 FAIL입니다. 실패 원인을 **데이터/스키마 문제, 로직 문제, 수치 비교 문제** 세 가지로 나눠 진단했습니다.

| 원인 분류 | 해당 케이스 | 진단 근거 |
|---|---|---|
| 데이터/스키마 문제 | 없음 (data.json) | 키 형식, 필터 존재, 라벨, 배열 크기 검증을 모두 통과함. bad_data.json의 오류 7건은 이 분류에 해당하며 검증 단계에서 걸러짐 |
| 로직 문제 | 없음 | 모드 1에서 손으로 계산한 값(1.0/5.0, 3.0/4.0)과 프로그램 결과가 일치하고, PASS 3건도 정상 판정됨 |
| **수치 비교 문제** | **size_5_1, size_13_2, size_25_1** | 두 점수가 수학적으로 같지만 부동소수점 오차로 끝자리가 다름 → epsilon 정책에 따라 동점(UNDECIDED) 처리 |

**왜 수학적으로 동점인가**: data.json의 필터는 0과 1만이 아니라 가중치가 조정되어 있습니다.

| 케이스 | Cross 필터와 겹치는 값 | X 필터와 겹치는 값 | 수학적 점수 |
|---|---|---|---|
| size_5_1 (X 패턴) | 중앙 0.9 × 1칸 | 대각선 0.1 × 9칸 | 0.9 = 0.9 |
| size_13_2 (Cross 패턴) | 선 0.3 × 25칸 | 중앙 7.5 × 1칸 | 7.5 = 7.5 |
| size_25_1 (X 패턴) | 중앙 4.9 × 1칸 | 대각선 0.1 × 49칸 | 4.9 = 4.9 |

**왜 끝자리가 달라지는가**: 0.1과 0.3은 2진수로 정확히 표현되지 않는 수(10진수의 1/3 = 0.333…과 같은 경우)라서, 컴퓨터는 가장 가까운 근삿값을 저장합니다. 이 값을 9번, 25번, 49번 반복해서 더하면 작은 오차가 쌓여 `0.8999999999999999`, `7.499999999999997`, `4.899999999999999`가 됩니다. 반면 한 칸만 곱하는 쪽은 오차가 쌓이지 않아 `0.9`, `7.5`, `4.9`가 그대로 나옵니다. 두 점수의 차이는 1e-16 ~ 1e-15 수준으로, 기준값 1e-9보다 훨씬 작습니다.

**epsilon 정책이 없었다면**: `>`로만 비교하면 이 3건은 오차의 방향에 따라 판정이 정해져 size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross가 됩니다. 세 건 모두 expected와 다른 **오판**이며, 결과가 데이터의 의미가 아니라 덧셈 순서 같은 우연에 의해 정해집니다. epsilon 정책은 이런 경우를 근거 없는 판정 대신 "판정 불가"로 정직하게 보고합니다.

**정리**: 3건의 FAIL은 프로그램 오류가 아니라, 필터 가중치가 두 모양에 같은 점수를 주도록 설계된 데이터에 동점 규칙을 적용한 결과입니다. 이 결과는 과제가 요구한 비교 정책(`abs(a - b) < 1e-9`이면 동점)을 그대로 따른 것이므로 정책을 바꿔 PASS로 만들지 않았습니다. 라벨 정규화(`x`→X, `+`→Cross, `cross`→Cross)를 적용했기 때문에 표기 차이로 인한 FAIL은 0건입니다.

### 2. 시간 복잡도 분석

**이론: O(N²)**
`mac()`은 N×N 배열의 모든 칸을 이중 반복문으로 한 번씩 방문하며, 칸마다 곱셈 1번과 덧셈 1번을 합니다. 따라서 연산 횟수는 N²에 비례하고 시간 복잡도는 **O(N²)**입니다. 크기 N이 2배가 되면 연산량은 4배가 됩니다.

**측정 결과 (평균/10회, 실행 환경에 따라 값은 달라질 수 있음)**

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 연산 1회당 시간 |
|---|---|---|---|
| 3×3 | 0.0036 | 9 | 약 400 ns |
| 5×5 | 0.0068 | 25 | 약 272 ns |
| 13×13 | 0.0335 | 169 | 약 198 ns |
| 25×25 | 0.1182 | 625 | 약 189 ns |

**측정값과 N²의 관계**

| 비교 | 연산 횟수 비율 | 시간 비율 |
|---|---|---|
| 3×3 → 5×5 | 2.78배 | 1.89배 |
| 5×5 → 13×13 | 6.76배 | 4.93배 |
| 13×13 → 25×25 | 3.70배 | 3.53배 |
| 3×3 → 25×25 | 69.4배 | 32.8배 |

**해석**
- 크기가 커질수록 시간도 함께 늘어나며, 13×13 → 25×25 구간에서는 연산 횟수 비율(3.70배)과 시간 비율(3.53배)이 거의 같습니다. 이는 실행 시간이 N²에 비례한다는 근거입니다.
- 작은 크기에서 시간 비율이 N² 비율보다 작은 이유는 **고정 비용** 때문입니다. 함수 호출, 변수 초기화, 반복문 준비처럼 크기와 무관하게 매번 드는 시간이 있어서, 연산이 9번뿐인 3×3에서는 이 비용이 전체 시간의 큰 비중을 차지합니다.
- 그 증거로 **연산 1회당 시간**이 400 → 272 → 198 → 189 ns로 줄어들다가 일정한 값에 수렴합니다. N이 커질수록 고정 비용의 비중이 작아지고, 전체 시간이 "연산 1회 시간 × N²"에 가까워집니다. 즉 시간 = (고정 비용) + (상수 × N²) 꼴이며, N이 커지면 N² 항이 지배하므로 O(N²)입니다.
- 측정 시간은 매우 짧아서(마이크로초 단위) 다른 프로그램 실행 등 PC 상태에 따라 실행할 때마다 조금씩 달라집니다. 그래서 워밍업 1회 후 10회 평균을 사용했습니다.

**NPU와의 연결**: 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로, 반복문으로 하나씩 계산하는 방식(CPU의 직렬 처리)으로는 연산량이 N²에 비례해 급격히 늘어납니다. NPU는 이런 MAC 연산 수천 개를 동시에 처리(병렬 처리)해 이 문제를 해결합니다.

### 3. 보너스: 1차원 최적화 결과 분석

**결과 요약**: 1차원 방식은 작은 크기(3×3 ~ 13×13)에서 약 25~40% 빨랐지만, 25×25 이상에서는 효과가 거의 사라졌습니다.

**작은 크기에서 빨라진 이유**: 2차원 방식은 행마다 안쪽 반복문을 새로 시작하고 `pattern[i]`로 행을 찾는 준비 작업을 합니다. 이 비용은 행 개수(N)에 비례합니다. 3×3에서는 전체 계산이 9번뿐이라 이 준비 비용의 비중이 크고, 1차원 방식은 이것을 없애서 눈에 띄게 빨라집니다.

**큰 크기에서 효과가 사라진 이유**: 크기가 커지면 N에 비례하는 준비 비용보다 N²에 비례하는 실제 곱셈·덧셈 비용이 훨씬 커져서, 준비 비용을 줄인 효과가 묻힙니다. 또 하나의 이유는 **파이썬 리스트의 구조**입니다. C 언어 배열이나 NPU의 메모리에서는 숫자가 메모리에 연속으로 놓여 있어, 1차원으로 순서대로 읽으면 캐시를 잘 활용해 빨라집니다. 하지만 파이썬 리스트는 숫자 자체가 아니라 숫자 객체의 **주소(참조)**를 담고 있어, 1차원으로 펴도 실제 숫자들이 메모리에 연속으로 놓이지 않습니다. 그래서 하드웨어 수준의 메모리 접근 이점이 파이썬에서는 거의 나타나지 않습니다.

**시간 복잡도**: 두 방식 모두 모든 칸을 한 번씩 계산하므로 똑같이 **O(N²)**입니다. 1차원 최적화는 복잡도를 바꾸는 것이 아니라 상수(연산 1회당 비용)와 고정 비용을 줄이는 최적화입니다. 실제 NPU가 빠른 이유는 이런 접근 방식 개선보다, 수천 개의 MAC 연산을 **동시에(병렬로)** 처리하기 때문입니다.
